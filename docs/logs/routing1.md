# 路由协议

AI 代理收到用户请求后执行的决策树。前置路由（6 信号意图评分 + 5 路分叉）+ 主流程 14 阶段决策树。

## 前置路由（所有请求入口）

### 步骤 1：阅读上下文

始终执行。读取：
- `docs/baseline/context/project-context.md`
- `docs/baseline/context/codebase-map.md`
- `docs/baseline/context/conventions.md`

### 步骤 2：路径分叉
**琐碎修复？**
- 条件：单文件 + <15 行 + 无 API/DB/认证/权限/契约变更
- 路径：→ 阶段 ⑨-⑩（实施与验证）→ 阶段 ?（日志）

**纯信息问题？**
- 条件：概念/文档类问题，不需要代码变更
- 路径：→ 直接回答 → 退出

**Bug？**
- 表层 Bug（拼写错误、空指针防御、样式修正）：诊断 → 修复 → 验证 → 日志
- 契约级 Bug（触发 API/DB/认证/权限/部署变更）：切回主流程阶段 ①

**验证或审计工作？**
- 条件：用户要求验证或审计
- 路径：运行审计提示词 → 记录发现 → 修订文档（不经过实施阶段）



**功能 / 设计 / 架构 / 非琐碎实施？**
- 路径：进入主流程 ↓

### 步骤 3：扫描 active 计划

读取 `docs/work/plan-registry.md`，按 `docs/process/plan-lifecycle.md` 交互协议匹配用户意图。

## 主流程

> **阶段编号说明**：阶段 ④（设计基线编写）、⑦（实现方案设计）、?（集成测试）在当前模板中为可选阶段，仅在项目复杂度需要时启用。跳过它们不会影响核心流程闭环。


### 阶段 ①：收集原始输入

- **进入**：进入主流程
- **动作**：
  1. `docs/work/<branch>/` 不存在 → 创建
  2. 检查 `docs/work/input/` 是否有共享材料 → 有则读取
  3. 询问用户："请将相关材料放入 `docs/work/<branch>/`，或直接在聊天中描述需求"
  4. 用户在聊天中描述需求 → 写入 `docs/work/<branch>/discussion.md`（阶段 ② 的起点）
  5. 等待用户确认就绪
- **退出**：分支目录已创建，输入已就绪

### 阶段 ②：澄清模糊（条件触发）

- **触发**：源材料不完整 / 存在矛盾 / 多种解读合理
- **不触发**：材料清晰、边界明确、无歧义 → 跳过
- **动作**：使用 `docs/skills/engineering/grill-with-docs/SKILL.md` 执行逐个追问澄清
- **退出**：术语统一、边界明确、阻塞解除（详见技能文件的退出条件）

### 阶段 ③：合成需求

- **触发**：阶段 ② 通过或跳过
- **动作**：按 `docs/work/requirement-synthesis.md` 创建 `docs/work/<branch>/requirement.md`
- **退出**：明确范围 / 明确非范围 / 明确行为 / 未决问题标记为非阻塞或已解决
- **失败**：需求未达到可实施状态 → 回退阶段 ②，**不通过写薄弱的计划来假装已就绪**


### 阶段 ③.5：技术调研（条件触发）

- **触发**（满足任一）：
  - 涉及当前技术基线未覆盖的新技术 / 库 / 服务
  - 无现有代码模块可参考实现
  - 需求本身含技术选型决策
- **前置检查**：扫描 `docs/skills/tech/tech-*/SKILL.md` → 若已有匹配技能 → 直接加载，跳过本阶段
- **不触发**：纯 Bug 修复 / 文案样式调整 / 已有明确技术方案 / 已存在对应技能 → 跳过
- **动作**：使用 `docs/process/research/evaluation-framework.md` 执行技术评估（胶水开发优先）；产出 `docs/work/<branch>/research.md`
- **退出**：人类审查批准 → 生成 docs/skills/tech/tech-{技术名}/SKILL.md（可执行实现指南，source 字段指向 research.md）并注册到 skills/README.md → 进入阶段 ⑤；调研影响需求范围 → 回退阶段 ③ 修改需求

### 阶段 ⑤：更新稳定设计基线

- **触发**（满足任一）：
  - 新增功能
  - 修改现有功能的行为
  - 变更模块边界或技术决策
  - 新增或修改角色权限
- **不触发**：文案修改、样式修复、Bug 修复（不改变行为）、单文件局部编辑 → 跳过
- **动作**：
  - 若阶段 ③.5 触发：读取 `docs/work/<branch>/research.md` → 将选定的新技术/库/服务写入技术栈基线和模块边界文档（具体文件由 codebase-map 路由）
  - 更新 `docs/baseline/context/project-context.md`（应用行为基线变更时）
  - 更新 `docs/baseline/standards/`（技术规则变更时，按触发场景表定位文件）
  - 规范本体放 `docs/baseline/standards/`，conventions.md 维护索引
- **退出**：Design 与 Arch 交叉引用完整 / 文档描述当前基线而非协商历史

### 阶段 ⑥：文档审计（条件触发）

- **触发**：工作实质性 / 跨模块 / 存在未解决风险
- **不触发**：局部低风险编辑 → 跳过
- **动作**：使用 `docs/skills/audit/document-audit-prompt.md` 执行两步审计
  - 步骤 ① 机械校验：检查引用断裂、文件缺失、入口点真实性（shell 命令，pass/fail）
  - 步骤 ② 内容审计：审计范围缺口、伪需求、设计矛盾、代码漂移（语义判断，分级裁决）
- **退出**：步骤 ① 全部通过 + 步骤 ② 裁决为 `? 通过文档审计`
- **失败**：修订断裂引用或文档内容直到通过

### 阶段 ⑧：编写计划（条件触发）

- **触发**（满足任一）：
  - 变更 API、数据库/模型、认证、集成、部署或公共契约行为
  - 变更跨界面或多模块共享的行为
  - 涉及设计基线冲突或过时文档（阶段 ⑤ 审计发现的断裂）
  - 预计跨越多 AI 会话
  - 修改超过 5 个文件或预计超过 200 行变更
  - 存在无法通过单次实施直接消除的产品或技术风险
- **不触发**（无计划路径）：影响极少文件、有明确现有行为或测试、且不涉及契约、数据/模型结构、认证、权限、集成、部署、跨界面行为或过时文档冲突的局部低风险变更。满足全部条件时跳过 ⑧⑨?。
- **动作**：按 `docs/work/plan-authoring.md` 创建 `docs/work/<branch>/plan.md`
- **动作**（多阶段计划）：先呈现推荐（结构、阶段划分或子计划列表、依赖图），停等人类批准后再写文件
- **退出**：计划已写入 `docs/work/<branch>/plan.md` 且满足 `docs/work/plan-authoring.md` 退出标准
- **退出时**：将计划写入 `docs/work/plan-registry.md`（"全部计划"段，状态 ?）
- **失败**：不满足退出标准 → 修订直到通过

### 阶段 ⑨：计划审计（创建计划则强制）

- **进入**：阶段 ⑧ 产出计划
- **动作**：使用 `docs/skills/audit/plan-audit-prompt.md` 独立挑战计划
- **退出**：计划通过审计
- **失败**：阻塞性发现 → 修改计划 → 重审（循环直到通过）

### 阶段 ⑩：实施与验证

- **进入**：阶段 ⑧ 通过，或属无计划路径
- **进入时**：将 frontmatter `status` 改为 `in-progress`，更新 plan-registry（无计划路径跳过）
- **进入时**：更新 `docs/work/plan-registry.md`（"当前激活"，状态 ??）

- **动作**：
  1. 读取 plan.md，锚定实施范围（触及面 + 公共契约 + 非目标），提取测试矩阵（验收标准→测试断言）

  2. 按 `docs/skills/engineering/tdd/SKILL.md` 技能执行 TDD 循环（RED→验证RED→GREEN→验证GREEN→REFACTOR）
     - 编辑纪律：后端数据路径用结构化解析；编辑紧贴模块边界；只在消除真实复杂度或匹配既有模式时才加抽象

  3. 每次 GREEN 确认时叠加分层验证：单元 → 集成 → 证据包
  4. 阶段出口：加载 `docs/skills/engineering/verification-checklist/SKILL.md` 逐条打勾
  5. 阶段出口：使用 `docs/skills/audit/code-quality-audit-prompt.md` 审计本次变更文件，P0/P1 发现即阻断

  6. 证据硬规则：所有验证必须实际执行并捕获输出；禁止从记忆或推理中声称结果；占位符命令不等同于通过

- **退出**：验证检查清单全部打勾 + 代码质量审计 P0/P1 零发现 + 全量验证命令通过且输出已捕获
- **失败**：从当前 RED-GREEN-REFACTOR 断点修复继续
- **设计缺陷**：→ 回退阶段 ⑤
- **无测试框架**：首个切片 → 搭建测试基础设施；搭建完成前以运行时验证矩阵（见 `docs/skills/engineering/verification-checklist/SKILL.md`）为最低标准
- ### 阶段 ?：闭环审计（创建计划则强制）

- **进入**：阶段 ⑩ 完成且计划已创建
- **动作**：使用 `docs/skills/audit/closure-audit-prompt.md` 独立复核
- **退出**：闭环关卡全部满足
- **退出时**：将 frontmatter `status` 改为 `completed`，从 plan-registry 删除该行
- **退出时**：更新 `docs/work/plan-registry.md`（移至"已完成"段，清除"当前激活"）
- **失败**：关卡未过 → 回退阶段 ⑩
### 阶段 ?：日志 / 回归 / 回顾

- **进入**：阶段 ⑩ 通过或无计划路径完成
- **动作**：
  1. 追加每日开发日志到 `docs/logs/YYYY/MM-DD.md`（倒序，参照 `docs/logs/00-log-writing-guide.md`）
  2. 检查 `docs/logs/error-patterns.md` → ≥2 次重复模式 → 触发阶段 ?
  3. 非显而易见回归 → 记录到 `docs/bugs/`（参照 `docs/bugs/00-bug-fix-note-writing-guide.md`）
  4. 原型与实施实质性偏离 → 编写回顾到 `docs/retro/`（参照 `docs/retro/00-retrospective-writing-guide.md`）
- **退出**：日志已写入

### 阶段 ?：技能提取（条件触发）

- **触发**：相同错误模式反复出现 ≥2 次（经 `docs/logs/error-patterns.md` 追踪）
- **不触发**：偶发错误 → 跳过
- **动作**：评估 → 提升为 `docs/skills/` 下的可复用审计提示词/检查清单/Lint 规则
- **退出**：新技能或审计条目已创建

## 主流程总览

| 阶段 | 类型 | 触发条件 |
|------|------|---------|
| ① | 始终执行 | 任何非平凡工作 |
| ② | 条件 | 材料不完整或矛盾 |
| ③ | 条件 | 阶段 ② 触发了或材料已经可合成 |
| ③.5 | 条件 | 新技术/库/服务，无现有模块，含技术选型决策 |
| ⑤ | 条件 | 新增功能 / 修改行为 / 变更模块边界 / 变更角色权限 |
| ⑥ | 条件 | 实质性 / 跨模块 / 有风险 |
| ⑧ | 条件 | 满足计划触发规则 |
| ⑨ | 条件 | 阶段 ⑧ 产出计划 |
| ⑩ | 始终执行 | — |
| ? | 条件 | 阶段 ⑨ 执行过 |
| ? | 始终执行 | — |
| ? | 条件 | 相同错误 ≥2 次 |
