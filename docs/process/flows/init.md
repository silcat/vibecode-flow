# 初始化

## 用途

项目初始化入口。当用户请求初始化项目（新项目或已有项目接入）时进入本文件。

初始化流程覆盖从模板占位符到可开始编码的完整过渡。分两个场景：
- **场景 A**：新项目——从零开始，按需填充基线
- **场景 B**：已有项目接入——先勘测代码，再提取约定，最后探针验证

## 首先阅读

- [routing.md](../routing.md) — 路由表，本文件是路由目标之一
- [intent-detect.md](../intent-detect.md) — 初始化触发判定
- [START-HERE-after-copy.md](../../../START-HERE-after-copy.md) — 原始初始化清单（本文件为其正式流程化版本）
- [project-context.md](../../baseline/context/project-context.md) — 项目上下文模板

## 场景判定

读取 `project-context.md`，按以下条件判定场景：

| 条件 | 场景 |
|------|------|
| `project-context.md` 含 `<项目名称>` 且 codebase-map.md 入口点为空 | 场景 A：新项目 |
| 仓库已有实际代码（存在 pom.xml / build.gradle / package.json / go.mod / Cargo.toml 等） | 场景 B：已有项目接入 |

判定后进入对应场景序列。两场景在流程管理阶段汇合。

## 场景 A：新项目初始化

> 设计哲学：不要为了填满基线而阻塞第一个功能。需要什么加什么。

### 场景 A 序列

| 步骤 | 执行者 | 任务 | 完成证明 |
|------|--------|------|---------|
| A1 | AI | 搜索全仓占位符（`<项目名称>`、`<填入>`、`<路径>`、`<风险>`、`<project-name>`），列出清单并标注是否可自动替换 | 输出占位符清单 |
| A2 | Human | 提供项目名称、目标技术栈（语言/框架/数据库/中间件） | project-context.md 中填入实际值 |
| A3 | Human | 提供真实验证命令（安装依赖/编译/测试/运行） | 验证命令非占位符且可执行 |
| A4 | AI | 删除 humans 标记为不使用的可选目录（`docs/skills/`、`docs/retro/`、`docs/baseline/architecture/`、`docs/baseline/standards/` 中的按需项） | 目录已删除或 human 确认保留 |
| A5 | AI | `codebase-map.md` 入口点填入"待创建"，其余留空 | 入口点表非全空 |
| A6 | AI | `conventions.md`：删除不适用的规范路由行，框架名替换为实际选型 | 路由行与实际技术栈一致 |
| A7 | Mixed | `standards/`：按需写——第一个需求用到什么就写什么，其余保留作参考 | 触发场景所需的标准文件就位 |
| A8 | Mixed | `architecture/`：按需写——单模块只写 module-internals.md，多服务再补边界 | 架构文件与当前规模匹配 |
| A9 | Human | 原始输入材料放入 `docs/work/input/` | 文件存在 |
| A10 | Mixed | 需求文件写入 `docs/work/` | 需求文件存在且有验收标准 |
| A11 | AI | 更新 `plan-registry.md`（若项目使用） | registry 条目完整 |
| A12 | AI | 创建 `docs/logs/{年份}/` 目录 | 目录存在 |

### 场景 A 阻塞条件

以下任一未完成，禁止开始编码：

- `project-context.md` 仍为模板空白（含 `<项目名称>` 占位符）
- 验证命令是占位符
- 活跃需求没有验收标准
- 活跃需求不在 `plan-registry.md` 中（若使用 registry）

### 场景 A 最短路径（~25 分钟）

```
A2-A3（10 分钟）→ A5（1 分钟）→ A9-A10（10 分钟）→ A3 验证命令确认 → 开始编码
```

## 场景 B：已有项目接入

> 设计哲学：先勘测再做，先记录再改。第一个需求是探针，验证整套机制能否转起来。

### 场景 B 阶段 1：勘测（硬门檻，必须做完才能写代码）

| 步骤 | 执行者 | 任务 | 完成证明 |
|------|--------|------|---------|
| B1.1 | AI | 从构建文件提取实际技术栈和版本，写入 project-context.md | project-context.md 技术基线非空 |
| B1.2 | AI | 从配置文件提取实际外部平台连接 | project-context.md 外部平台表非空 |
| B1.3 | AI | 运行一次真实验证命令，记录结果 | 命令输出已记录 |
| B1.4 | AI | 文档新鲜度标记为 `stale` | project-context.md 新鲜度 = `stale` |
| B1.5 | AI | 遍历目录树，填写 codebase-map.md：模块清单 + 入口文件 + 跨模块通信方式 | 入口点表和常见变更路由表非空 |
| B1.6 | AI | codebase-map.md：标注脆弱文件和常见变更路径 | 大型或脆弱文件表非空 |
| B1.7 | AI | 从代码反推服务清单 + 依赖拓扑，写入 module-boundaries.md | 模块清单非空，依赖图就位 |
| B1.8 | Mixed | AI 检测异常（循环依赖、跨模块直查），Human 确认 | 异常已标注类型 |
| B1.9 | AI | 解剖一个典型模块，画实际分层 + 异常跨层调用，写入 module-internals.md | 分层图就位 |
| B1.10 | AI | 追踪 2-3 个核心跨模块流程的调用序列，写入 business-flows.md | 流程序列就位 |
| B1.11 | AI | 记录真源冲突到 `docs/work/input/drift-inventory.md` | 冲突清单就位 |
| B1.12 | Human | 每个冲突标记类型：`实施漂移` / `文档漂移` / `有意遗留` | 所有冲突已分类 |

### 场景 B 阶段 2：提取约定（实施前按触发场景补）

| 步骤 | 执行者 | 任务 | 完成证明 |
|------|--------|------|---------|
| B2.1 | AI | 扫描代码提取实际编码模式，生成对应 standard 文件 | standards/ 文件就位 |
| B2.2 | Human | 代码风格有分歧 → 裁决后写入 discussion.md | discussion.md 就位或无需裁决 |
| B2.3 | AI | conventions.md：删除不适用路由行，全局约定对齐实际工具链 | 路由行与项目一致 |

### 场景 B 阶段 3：第一个需求（探针）

| 步骤 | 执行者 | 任务 | 完成证明 |
|------|--------|------|---------|
| B3.1 | Human | 选第一个任务：修复已知 bug / 加简单字段 / 补单元测试 → 禁止重架构 | 任务选定 |
| B3.2 | AI | 走完整闭环：意图检测 → 路由 → 收集 → 计划 → 实施 → 日志 | 闭环完成，日志已写 |
| B3.3 | Mixed | 哪步卡住就补对应文档 | 文档补齐 |

### 场景 B 阶段 4：持续校准（每个需求后）

| 步骤 | 执行者 | 任务 | 触发条件 |
|------|--------|------|---------|
| B4.1 | AI | 更新 `docs/logs/` | 每次变更后 |
| B4.2 | AI | 更新 architecture/ | 变更影响架构事实 |
| B4.3 | Mixed | AI 识别新模式，Human 确认后写入 standards/ | 变更产生新约定 |
| B4.4 | AI | 更新 codebase-map | 脆弱文件位置变了 |
| B4.5 | Mixed | 积累 3-5 个需求后做基线审计：AI 逐文件核对，Human 确认 → `stale` 改 `fresh` | 累计 ≥3 个需求且全部闭环 |

### 场景 B 阻塞条件

以下任一未完成，禁止开始编码：

- codebase-map.md 入口点表全空
- 保护区未定义但有明显不能碰的模块
- 核心模块边界未勘测 → 禁止动跨模块代码
- 真源冲突未记录 → 禁止静默选边
- project-context.md 仍为模板空白
- 验证命令是占位符
- 活跃需求没有验收标准

### 场景 B 最短路径（~2 小时）

```
B1.1-B1.2（30 分钟）→ B1.5（30 分钟）→ B1.7（20 分钟）→ B1.9（15 分钟）→ B1.11（10 分钟）→ B3 选最小需求走闭环验证 → 开始编码
```

## 退出条件

两场景均在完成全部序列步骤后，进入 [process-management](stages/process-management/README.md) 阶段记录日志，然后退出。

场景 A 完成后，项目基线就绪，后续请求按标准路由（Bug / 快速模式 / 需求）进入正常流程。

场景 B 阶段 1-2 完成后，项目文档基线就绪；阶段 3 探针闭环完成后，验证整套机制可用；阶段 4 为持续迭代中的校准动作。

## 分工速查

| AI 能做 | 人类必须做 |
|---------|-----------|
| 读代码、跑命令、分析结构、写文档 | 给名字、定规范、判意图、裁决冲突 |
| 勘测现有代码生成报告 | 判断"已知问题"还是 bug |
| 检测不一致并列出清单 | 决定修代码还是修文档 |
| 按人类说的规范写 standards | 说清楚规范是什么 |
| 遍历目录树画拓扑 | 选哪个模块做典型解剖 |

## 更新原则

- 新增场景步骤 → 同步更新序列表和完成证明
- 阻塞条件变更 → 仅修改本文件阻塞条件段
- START-HERE-after-copy.md 有变更 → 评估是否需同步到本文件
- 新增可选目录 → 在 A4 步骤中更新
