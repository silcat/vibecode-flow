# 摸底

## 目的

仅限信息收集。理解**存在什么**，不是**可能有什么**。

研究质量与阶段纯度一样重要。不是收集事实——是验证事实、交叉核对、将稳定证据与推测区分开来。

研究覆盖**内部范围**（代码库、架构、现有模式）和**外部范围**（库文档、生态系统上下文、最佳实践、官方文档）。

## 进入条件

requirement.md 存在且 requirement 阶段完成证明通过。

## 执行步骤

### 1. 内部调研

读 requirement.md，提取关键词。在代码库中搜索：

- 读 `docs/baseline/architecture/module-boundaries.md`，确定涉及模块
- 读 `docs/baseline/architecture/system-baseline.md`，理解技术全景
- grep 相关类名、接口名、注解，理解现有模式
- 读 `docs/baseline/context/project-context.md` 中相关技术栈信息
- 读 `docs/baseline/standards/` 中受影响的标准文件

证据要求：每个发现必须附具体文件路径 + 行号。不含推断。

### 2. 能力覆盖分析

对照 requirement.md 每条验收标准，逐条判断现有代码的覆盖情况：

| AC | 现有能力 | 缺口 | 证据 |
|----|---------|------|------|
| AC-1 | 模块 X 已有 Y | 缺 Z / 已覆盖 | [文件:行号] |

### 3. 外部调研

涉及新技术/库/服务且无现有模块可参考时执行。否则跳过。

当涉及库、供应商、标准、最佳实践或生态系统指南时：

- 优先使用官方文档、维护者、规范和主要来源
- 重要声明在多个独立来源之间交叉核对
- 信息具有时效性时，标注日期和新鲜度
- 将权衡证据作为观察结果报告，而非建议
- 捕获矛盾之处，不掩盖
- 如果调研开始滑向方案选择，停止并移交给方案阶段

仅收集事实：版本、成熟度、许可证、维护状态。不做方案对比、不做推荐。

### 4. 第一性原理拆解

1. 写出当前理解的结论
2. 逐条追问：这个结论依赖哪些前提？
3. 区分事实、假设、偏好、惯例
4. 保留不可再拆的事实约束

### 5. 写入模板

按 `template.md` 填写，产出 `docs/work/<branch>/investigate.md`。

## 红线

- 不写"推荐方案 X"
- 不写"方案 A 优于方案 B"
- 不说"应该选"
- 不含未标注来源的推断
- 违反上述任一 → 删除违规内容，重写

## 产出物

| 产出 | 路径 |
|------|------|
| 摸底报告 | `docs/work/<branch>/investigate.md` |

## 完成证明

`Test-Path` 确认 investigate.md 存在。文件中不包含推荐性或决策性语言。逐条发现附证据来源。

## 完成报告

完成证明通过后，输出以下块：

```
**总结：** [1-2 句话总结本阶段产出]
**阻塞/顾虑：** [仅在有阻塞或顾虑时出现此字段]
**下一步：** 当前命中 [退出路由中的实际条件]，等待人类确认后进入 [对应去向]。
```

## 退出路由

完成证明通过后，等待人类确认才进入下一阶段。禁止自动推进。

| 条件 | 去向 |
|------|------|
| 完成 | → solution |
| 摸底发现需求不可行 | → requirement（携带缺口清单） |
