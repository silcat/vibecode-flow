# 计划审计提示词

在实施前审计执行计划时使用此提示词。所有创建的计划都需要此审计。

## 触发

阶段 plan 产出计划后，进入阶段 plan-audit 时执行。

## 分型路由

审计开始前，读取计划 frontmatter `type` 字段决定审计模式：

| type | 审计模式 | 计划类型 |
|------|---------|---------|
| `master` | 总计划审计 → 读取 §总计划审计 |
| `standalone` | 单计划审计 → 读取 §单计划审计 |
| `sub` | 子计划审计 → 读取 §子计划审计 + §单计划审计 |

子计划审计 = 单计划审计的所有检查项 + 子计划特有检查项。

---

## 总计划审计

将总计划作为**编排契约**审计。

### 聚焦领域

- **拆分合理性**：子计划是否各自独立可交付？边界是否重叠（两个子计划改同一模块同一层）或遗漏（没有任何子计划覆盖需求的某个验收标准）？
- **依赖图正确**：无环（可用 DFS 检验）、覆盖清单中全部子计划、依赖方向符合模块间实际调用关系
- **集成关卡真实**：每条可验证（不是"确认系统正常"）、不重复子计划各自的闭环关卡、覆盖跨计划行为（集成点、数据一致性、端到端流程）
- **章程完整**：北极星 / 完成定义 / 安全硬约束 / 明确不做的——是否可作为子计划范围争议的裁决依据？
- **编排可行**：子计划清单的并行声明与依赖图是否一致？并行组内的子计划是否真的无共享状态？

### 严重程度

| 级别 | 定义 |
|------|------|
| 阻塞 | 依赖图有环、子计划覆盖缺口、集成关卡不可验证 |
| P1 | 依赖方向与模块调用关系矛盾、拆分重叠导致冲突 |
| P2 | 章程不完整导致范围争议无法裁决、并行声明与依赖图矛盾 |
| P3 | Skill 未标注、格式不完整 |

---

## 单计划审计

适用于 `standalone` 和 `sub` 类型。将计划作为**实施契约**审计。

### 聚焦领域

- **当前基线是否诚实**：是否如实描述技术现状？
- **目标与非目标是否清晰**：范围边界是否无歧义？
- **闭环关卡是否真实**：可验证，还是空洞承诺？
- **隐藏依赖**：依赖了计划未声明的模块、技术或前置条件？是否存在未解决的需求缺口？
- **沉默降级**：范围内的缺陷或契约缺口是否被静默降级？
- **任务路由与技能标注是否诚实**：必要、匹配所有者文档？
- **AI 自治边界**：是否未经人类确认就松动了待办或上下文？
- **陈旧文档或遗留模式冲突**：是否在实施前分类？
- **证明与验证**：是否覆盖每一条验收标准？
- **测试矩阵**：行数是否等于验收标准条目数？

### 前置合规

- 计划中的操作是否匹配 `ai-autonomy-policy.md` 的自治级别？
- 是否触碰保护区而未获批准？
- 验证命令是否与 `project-context.md` 对齐且非占位符？
- 审查者可用性：冷重放不是第二审查者，不批准保护区/未解决风险/真源冲突

### 严重程度

| 级别 | 定义 |
|------|------|
| 阻塞 | 范围或闭环存在根本性缺陷，计划不可执行 |
| P1 | 隐藏依赖或需求缺口导致实施路径错误 |
| P2 | 可测试性不足，验证阶段无法证明完成 |
| P3 | 次要表述不一致、Skill 标注不精确或格式不完整 |

## 子计划审计（增量）

在单计划审计全部检查项基础上，增加：

### 额外检查

- **范围对齐**：子计划目标是否在总计划分配给它的范围内？是否存在范围蔓延（做了总计划未分配的验收标准）？
- **依赖前提正确**：子计划声明的依赖是否确实是本子计划的必要前置？（防止所有子计划都依赖同一个，形成假瓶颈）
- **并行安全**：本子计划与总计划中声明为可并行的其他子计划，是否修改了同一公共契约或同一模块的同一层？（并行冲突时，要么取消并行标记，要么调整边界）

### 严重程度

| 级别 | 定义 |
|------|------|
| 阻塞 | 范围蔓延导致与总计划分配矛盾、并行冲突未处理 |
| P1 | 不必要的依赖导致编排瓶颈 |
| P2 | 范围边界模糊但尚未冲突 |

---

## 输出格式

按严重程度降序排列发现。每个发现：标题 / 严重程度 / 受影响文件 / 当前缺口 / 风险 / 建议。

裁决：

```
PASS: 通过计划审计
残余风险：[逐条列出，无则写"无"]

FAIL: 需要修改
阻塞项：[逐条列出]
```

除非改变了风险评估，否则不要赞扬计划。
