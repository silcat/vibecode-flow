# 需求与基线审计提示词

在计划编写前审计需求→基线链路是否完整、正确、可被计划。

触发条件：工作实质性 / 跨模块 / 存在未解决风险。局部低风险编辑跳过。

## 工作流

审计分两步：先做机械校验（可脚本化的检查），再做内容审计（需要判断的语义检查）。

### 步骤①：机械校验

对以下检查项逐条执行，不依赖 AI 判断——文件在就是在，不在就是不在，值冲突就是冲突。

| # | 检查项 | 方法 |
|---|--------|------|
| 1 | 活跃需求路径存在 | `Test-Path` 读取 `docs/work/registry.md`，逐条验证当前激活项中各工作目录下的 `requirement.md` |
| 2 | 活跃所有者文档路径存在 | `Test-Path` 读取 `docs/work/registry.md` 当前激活项，验证 requirement.md 中引用的所有所有者文档路径是否存在 |
| 3 | 需求文件内部引用断裂 | `rg` 提取需求文件中所有 `docs/` 路径引用，逐条 `Test-Path` |
| 4 | 架构文档交叉引用断裂 | `rg` 提取 `docs/baseline/architecture/` 中所有 `docs/` 路径引用，逐条 `Test-Path` |
| 5 | 代码地图入口点真实 | 对照 `codebase-map.md` 的入口路径，逐条 `Test-Path` |
| 6 | 验证命令可执行 | 对照 `project-context.md` 的验证命令表，逐条确认命令目标文件存在（不是占位符） |
| 7 | 基线交叉引用无断裂 | 检查 system-baseline.md 和 project-context.md 中新增技术的引用路径 |
| 8 | 跨文件同义字段一致性 | 提取 `project-context.md`、`system-baseline.md`、`module-boundaries.md` 中共同声明的字段（架构模式、技术栈版本、端口、服务清单），逐对比较。冲突 = 断裂 |

每项输出 `PASS: 通过` 或 `FAIL: 断裂：[具体路径及冲突内容]`。断裂项全部修复后才能进入步骤②。

### 步骤②：内容审计

#### 聚焦领域

审计需求→基线的完整性和正确性：

- **需求完整性**：验收标准是否可逐条测试？边界是否清晰（明确非范围）？关键业务规则是否有隐含假设？
- **调研可信度**（若触发调研阶段）：research.md 的维度评估是否基于真实数据？弃用方案理由是否充分？推荐结论是否有数据支撑？
- **基线一致性**：写入的技术栈/模块边界/行为描述是否跨文件一致？交叉引用是否全部可达？同一事物是否只在单一文件中定义（归权责）？
- **需求可计划性**：从当前需求文档出发，能否写出明确分步的实施计划？有无关键信息缺失导致计划无法编写？
- **模板残留**：基线文件是否仍含 `<!--` 注释指令、`<项目名称>` 等占位符、或"填完后删掉"类未完成标记？存在则基线不可信，应先完成模板填充。
- **新鲜度自洽**：`project-context.md` 声明的文档新鲜度是否与自治级别兼容？（`unknown` + `实施` = 矛盾）

#### 严重程度

| 级别 | 定义 |
|------|------|
| 阻塞 | 范围缺失、需求矛盾、或架构冲突导致无法编写计划 |
| P1 | 需求与基线矛盾，关键规则缺失，或跨文件不一致导致实施必出错 |
| P2 | 未决问题被当作已确定需求，调研证据薄弱，或模板残留 |
| P3 | 次要文档不一致、引用不精确、或新鲜度标注不准确 |

#### 输出格式

按严重程度降序排列发现。每个发现包含：标题 / 严重程度 / 受影响文件 / 当前缺口 / 风险 / 建议。
最后裁決：

```
PASS: 通过需求与基线审计
残余风险：[逐条列出，无则写"无"]

FAIL: 需要修改
阻塞项：[逐条列出]
```

## 与其他审计的关系

- 需求与基线审计（本文件）关注需求→基线的完整性和正确性（计划前）
- 计划审计（`../plan-audit/audit-prompt.md`）关注执行计划的可行性和闭环设计（计划产出后）
- 闭环审计（`../closure/audit-prompt.md`）关注实施是否真正匹配计划和需求（实施完成后）

三个阶段按顺序接力，不互相替代。
