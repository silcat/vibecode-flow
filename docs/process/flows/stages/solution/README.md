# 方案

## 目的

基于摸底报告的事实约束，生成备选方案、应用思维模型对比、做出决策。产出 PRD——选定技术路线和架构方案。

方案阶段的衡量标准不是"选了一个方案"，而是**被拒方案都有明确的否决原因，选定方案经得起逆向推敲**。

## 进入条件

investigate.md 存在且 investigate 阶段完成证明通过。

## 执行步骤

### 1. 加载输入

- 读 investigate.md 的基础事实和约束清单
- 读 requirement.md 的验收标准和范围

### 2. 生成备选方案（至少 2 个）

每个方案标注：

| 维度 | 说明 |
|------|------|
| 涉及模块 | 需要修改或新建的模块 |
| 变更估算 | 预估新增/修改的文件数（数量级，非精确） |
| 新增依赖 | 新引入的库、服务、中间件 |
| 架构影响 | 新服务、DB 变更、通信方式变更 |

涉及外部依赖选型时，对候选依赖按以下维度评估：

| 维度 | 评估内容 |
|------|---------|
| 功能匹配 | 需求覆盖率？缺口能否通过插件补上？是否过度设计？ |
| 技术质量 | 生产验证案例？性能基准？CVE 历史？错误模型清晰度？ |
| 集成成本 | 技术栈兼容？胶水代码量？传递依赖数量？ |
| 可维护性 | API 设计质量？主版本升级成本？测试友好度？ |
| 社区生态 | 维护活跃度？Star 趋势？文档质量？生态插件？ |
| 团队匹配 | 学习曲线？许可证兼容？供应商风险？ |

评估结果引用 investigate.md 的外部参考，不重新查文档。

### 3. 思维模型对比

对每个方案应用：

| 模型 | 问题 |
|------|------|
| 奥卡姆剃刀 | 同等约束下，哪个方案假设最少、依赖最少、状态最少？ |
| 逆向思维 | 每个方案怎样一定会失败？失败路径能否内置阻断点？ |
| 多阶思维 | 方案实施后：后续需求受什么影响？维护成本怎么变？ |
| 状态空间思维 | 决策是否可逆？是否堵死后续演进路径？回滚代价多大？ |

### 4. 写入模板

按 `template.md` 填写，产出 `docs/work/<branch>/solution.md`。

## 红线

- 只有一个方案 → 不合格，退回补至少一个备选
- 备选方案被拒但未标注核心否决原因 → 不合格
- 推荐结论无决策依据（未引用 investigate.md 的事实或思维模型对比）→ 不合格

## 产出物

| 产出 | 路径 |
|------|------|
| 方案文档（PRD） | `docs/work/<branch>/solution.md` |

## 完成证明

```
::solution-check
- 候选方案数：[N]（≥2 ✓ / ✗）
- 被拒方案均有否决原因：✓ / ✗
- 思维模型对比矩阵已填写：✓ / ✗
- 决策摘要完整（选定 + 被拒 + 理由）：✓ / ✗
- 结论段待人类审查批准：✓ / ✗
::solution-check
```

任一 ✗ → 阶段不完整，禁止退出。

## 完成报告

完成证明通过后，输出以下块：

```
**总结：** [1-2 句话总结本阶段产出]
**阻塞/顾虑：** [仅在有阻塞或顾虑时出现此字段]
**下一步：** 当前命中 [退出路由中的实际条件]，等待人类确认后进入 [对应去向]。
```

## 退出路由

完成证明通过后，等待人类确认才进入下一阶段。禁止自动推进。

| 条件 | 去向 |
|------|------|
| 完成 | → scope |
| 所有方案均不可行 | → requirement（携带否决原因清单） |
| 摸底信息不足 | → investigate（携带补充调研条目） |
