# 从规格驱动开发到吸引子引导工程

`nop-chaos-flux` 是一个基于 React 19、Zustand 5 和 Vite 8 构建的低代码运行时框架。它受百度 AMIS 启发，但围绕创新的设计原则从零开始独立重写。它包含 JSON Schema 编译器和运行时，以及报表设计器和流程设计器等设计工具。

该项目的初始版本由一名程序员在两个月内完成，完全通过自动化 AI 辅助开发。与普通的 AI 辅助开发不同，项目没有随着功能增多而质量下降。相反，模块边界越来越清晰，文档分类越来越稳定，测试和审计越来越能捕获真实问题，代码质量持续提升。

我最近做了几次内部分享，把这种实践命名为**吸引子引导工程**（Attractor-Guided Engineering，AGE）。后来在 code review 中发现，很多人其实还没真正理解。有些人的工作流接近随意的氛围编码。有些人用的是类似 OpenSpec 风格的规格驱动开发，整体倾向是任务驱动的、逐功能执行。随着工作积累，代码中的不一致也在稳步累积，偏离架构设计成为常态。

本文分析 AGE 与规格驱动开发之间的差异，以及普通业务项目能从 `nop-chaos-flux` 的大规模 AI 工程实践中学到什么。

## 核心层次

AGE 的核心是以下概念层次：

**状态空间 → 吸引子 → 轨迹 → 控制**

- **状态空间**：系统在当前约束下可能演化出的全部实施状态
- **吸引子**：系统在长期演化中被反复拉回的稳定结构
- **轨迹**：每一轮生成、验证、修正后留下的实际演化路径
- **控制**：通过局部信号持续影响轨迹的机制

仓库在已有约束下可能演化为的所有代码、文档、测试的组合，构成了状态空间。人类、AI、审查、CI、文档更新等延续性行动构成了演化规则。二者叠加产生的活仓库历史，就是轨迹。吸引子是在长期迭代中系统被反复拉回的稳定结构。

大规模 AI 开发本质上是一个动力系统中的受控收敛问题。AI 以极快速度扩展状态空间，关键不是到处加护栏，而是首先弄清楚系统长期应向什么结构回归。

吸引子不是写好的终点，不是路线图，也不是允许活动的边界。它是由少数高层约束隐式定义的结构：局部实现可以变化，但整体始终被这些关系拉回同一类形态。

在 `nop-chaos-flux` 中，最先定义吸引子的不是计划、Lint 规则、测试、审计或规格文件，而是 `docs/architecture/` 下带显式优先级的架构文档。在本文其余部分，这些带有所有者和优先级的架构文档被称为所有者文档（owner docs）。

`docs/architecture/README.md` 明确声明 `docs/architecture/` 是当前终态架构基线，`flux-design-principles.md` 是治理原则锚点，`frontend-programming-model.md` 拥有顶层原语和核心边界优先权，其他规范文档在各自主题内拥有局部优先权。

这些文档不枚举每一个正确实现。它们像方程一样定义了一个稳定结构：存在哪些原语、哪些依赖方向合法、哪些所有者边界不可破坏、哪些旧模式已不再属于正确状态空间。它们先定义了可持续的状态集群，只有在它们之后，实施、测试、计划、审计才有了参照点。

计划、验证、审计、日志、Bug、测试都在其后。它们本身不是吸引子，是让系统轨迹靠近吸引子的夹具。

Flux/AGE 不以规格演化为中心。它以吸引子定义和轨迹收敛为中心。

## 真实的开发历史

"架构文档定义吸引子"乍听像是普通的文档治理。但如果仔细看 `docs/logs/` 下的实际开发记录，差异就显现了。

例如，`docs/plans/371-deep-audit-2026-05-19-owner-routing-plan.md` 是一个典型的入口。它不直接编辑代码，而是将 `2026-05-19` 深度审计中保留的 64 项发现收敛为一份所有者路由基线。每项发现都有唯一的所有者桶、优先级、后继计划和所有者文档义务。没有无主问题，没有多主问题，也没有静默降级为模糊的 follow-up。

它的作用是将一轮偏离应当如何闭环冻结下来。后续的执行计划再将局部轨迹闭环到具体的结果切面。`docs/plans/382-deep-audit-2026-05-19-table-and-crud-owner-state-and-event-contract-plan.md` 闭环了表格/CRUD 的所有者状态和事件载荷：`当前基线` 声明了显式空数组所有者状态和事件载荷的实时状态，执行条目修复了空数组回退，聚焦测试证明了结果，`docs/components/table/design.md` 和 `docs/components/crud/design.md` 同步了所有者契约，最后全仓库 `pnpm typecheck`、`pnpm build`、`pnpm lint` 和 `pnpm test` 全部通过。独立闭环审计 `ses_1bd9ed593ffeVpkho4lb4wPR6p` 记录了 `裁决：可接受`。

`docs/plans/388-deep-audit-2026-05-19-form-tree-widget-accessibility-plan.md` 展示了另一种闭环。input-tree 和 tree-select 的可见节点 roving focus、`ArrowUp` / `ArrowDown` / `Home` / `End` 导航以及加载态 `aria-busy` / `aria-describedby` 都有聚焦证明，但计划明确裁定 `无需所有者文档更新`。这表明计划不只是任务清单，它还负责判断变更是否修改了所有者文档基线。

`docs/plans/400-deep-audit-2026-05-19-test-harness-reliability-plan.md` 和 `docs/bugs/62-e2e-shared-websocket-error-suppression-fix.md` 展示了记忆夹具的角色。问题不是业务功能出错了，而是 E2E 共享 fixture 过滤过宽，把真实传输/运行时失败也抑制了。修复不只是改代码，还增加了 `tests/e2e/fixtures-hard-gate.spec.ts` 证明 fixture 现在会失败，并记录了一条 Bug 记录规则：如果将来有测试真预期 WebSocket 失败，必须使用 per-test 豁免，且不得恢复 fixture 级的抑制。

`docs/logs/2026/05-19.md` 和 `docs/logs/2026/05-20.md` 不是日记。它们记录了每个闭环切片的聚焦证明、所有者文档裁定、全仓库关卡、独立审计和全绿基线。

这些材料构成了一条真实链条：所有者文档定义长期结构；审计发现偏离；计划路由并冻结所有权；聚焦证明展示局部结果；所有者文档裁定判断基线是否变更；日志、Bug、测试保存跨会话记忆；闭环审计从活仓库重新判断完成。

这就是 AGE 中的夹具。目标不是让每个任务看起来更完整，而是让系统轨迹持续回归吸引子。

## OpenSpec 结构上的强项

OpenSpec 是规格驱动开发的一个代表性框架。它很好地结构了一类工作：

- `openspec/specs/` 存储各能力的当前行为规格。
- `openspec/changes/` 存储变更提案，包括 `proposal.md`（为什么改、改什么、影响范围）、`design.md`（必要时写技术设计）、`tasks.md`（实施清单）。
- `changes/<name>/specs/` 用 `ADDED`、`MODIFIED`、`REMOVED`、`RENAMED` 记录规格增量。
- `archive` 按固定规则把增量写回主规格。

这个机制降低了更新规格的成本。OpenSpec 不要求 AI 每轮自由理解一整份需求然后随意编辑文档，而是用固定分段、需求标题匹配和增量应用，将结构化变更合并回主规格。在行为规格明确、需要可解析、可归档、且能一致写回的场合，这很有效。

## OpenSpec 的局限

OpenSpec 的规格格式——Requirement、Scenario、SHALL/MUST、增量段——对工具友好。但作为组织项目知识的通用方式，灵活性不够。

很多仓库知识天然不是 requirement/scenario 形态：

- 架构层次和优先级
- 术语误读的历史
- 外部调研材料如 PPT 和讨论记录
- 一次源码审计的结论
- 手动测试的观察
- 复杂 Bug 的诊断路径
- 为什么某个计划无法闭环

如果这些都必须先转为 spec/change 形态才能获得正式位置，转换成本高，且原始上下文会丢失。外部文档、讨论记录、分析报告、Bug 回顾可以直接成为仓库记忆。强行塞入 requirements/scenarios 反而会压平信息。

在执行验证上，两种方法也反映了不同的工具哲学。OpenSpec 的 `tasks.md` 是检查清单，`/opsx:verify` 是可选代理验证技能，需要通过扩展工作流手动启用。`archive` 检查任务状态并预警风险，但用户确认后仍可继续。严格闭环留给团队自行决定。

Flux 计划将独立闭环审计内建为必需路径。计划必须从当前基线出发，陈述`目标`和`非目标`，定义执行条目且每项标记为`修复` / `决策` / `证明`，并指定`闭环关卡`。在标记为`已完成`之前，独立子代理或审查者必须回到活仓库执行闭环审计。`docs/plans/361-slot-contract-host-manifest-and-owner-doc-closure-plan.md` 将当前基线、发现所有权矩阵、执行阶段、闭环关卡、已裁定的延期项和独立审查证据放在一起。这不是检查清单，它严格定义了完成条件并要求独立审计证据。**它强调的不是做了什么，而是做到什么程度才算真正落地。**

## 为什么规格驱动开发容易变成任务导向

规格驱动开发天然会把人和 AI 的注意力拉回"这个变更怎么完成？"

一个变更通常有 proposal、design、tasks、delta specs。这比口头需求好很多，但它天然围绕单个变更组织：为什么改、改什么、怎么做、哪些清单勾完了。久而久之，规格驱动开发很容易变成一个更正式的任务派发系统。

这种任务导向有一个隐蔽风险：规格更新了、任务勾完了、archive 跑了，AI 和人类都获得很强的完成感。但系统是否真的更接近其长期结构，不是变更本身能证明的，那需要对照架构文档、活仓库、测试、日志和独立审计来检查。

如果要维护 Flux 级别的规格精度，成本通常更高。Flux 不维护一棵规格树，而是维护一套不同职责的仓库记忆：架构文档定义吸引子；计划定义局部轨迹闭环；日志记录演化；Bug 保存复杂诊断；测试保存人类发现；分析保存研究判断；审计重新检查活仓库。把这些全部塞进 spec/change 结构，会导致持续的转换成本。

规格驱动开发可以是 AGE 内部管理行为规格演化的一个局部夹具，但它不应该替代架构文档，也不应替代计划闭环、日志、Bug、测试、审计等独立的仓库记忆。

## 如果只需要读一份所有者文档呢？

这体现了两种方法的根本差异。

在 Flux 中，如果只需要查渲染器运行时的当前所有者契约，可以直接从 `docs/index.md` 路由到 `docs/architecture/renderer-runtime.md` 及相关引用。不需要创建 change、写 proposal、定义 tasks，也不需要把问题重写成规格增量。

如果只是研究，可能去 `docs/analysis/`。如果是手动测试发现，去 `docs/testing/`。如果是复杂 Bug，去 `docs/bugs/`。如果是执行闭环，那就写计划。如果稳定基线变了，那就回到所有者文档。

Flux 的文档组织是自由的，但不是随意的。自由是指它不强制所有种类的知识都先经过同一产物工作流。受约束是指每种材料类型都有清晰的职责，不能随意声称事实权。

OpenSpec 的组织更结构化，适合把拟议行为变更装入一个 change 包并将规格增量写回主规格。但路由通用仓库知识不是它的默认主线问题。

## 任务不是计划

OpenSpec 的 `tasks.md` 并不对应 Flux 的 `plans`。

`tasks.md` 最多对应 Flux 计划内部的执行清单片段，或当前会话的 todo list。它帮助 AI 不漏步骤，但它不回答这些问题：

- 当前活仓库基线是什么？
- 此次变更明确不做什么？
- 哪些证据证明工作真正完成了？
- 哪些缺陷不能被降级为 follow-up？
- 谁独立审查完成？

Flux 计划的价值不是包含更多任务，而是一份局部轨迹的闭环契约。

所以任务对 AI 有用，但任务不是真源。`- [x]` 只表示实施者声称此项完成。真实的证明必须回到当前代码、测试、所有者文档和独立审查。

## 变更来源不只是规格变更

OpenSpec 有一条清晰的路径：围绕 specs 和 changes 组织行为规格演化。

Flux 的变更来源更广：

- 用户提出的新需求
- 阅读源码发现的架构偏移
- 审计发现的所有者边界问题
- 测试问题暴露的交互问题
- Bug 记录中记载的历史回归风险
- 外部研究或分析中的设计判断
- 计划闭环审计推翻早前的"已完成"判断

这些来源不一定要先变成规格增量。它们可能进入分析、测试、Bug、日志、计划，或直接更新架构文档。是否需要变成行为契约，取决于它们是否属于长期基线。

这就是 Flux 文档组织自由的意义：不同来源的信息先待在各自的地方，而不是全部塞进一条规格演化通道。

## 文件入/文件出为什么重要

我在分享中多次强调，AI 驱动开发的最佳实践之一是**文件入/文件出**。这不是文档洁癖，而是吸引子和夹具需要载体。

文件入：输入不应只停留在聊天窗口。即使内容乱，先写进需求文件、分析文件或计划文件，然后用 OpenCode 的 `@` 引用该文件。

文件出：输出不应只打印在窗口里然后消失。重要结论、分析、计划、测试记录、Bug 诊断、架构约束，都应写入 `docs/` 并按职责分类：

- 架构规则 → `docs/architecture/`
- 变更闭环 → `docs/plans/`
- 执行轨迹 → `docs/logs/`
- 手动测试发现 → `docs/testing/`
- 复杂缺陷诊断 → `docs/bugs/`
- 研究判断 → `docs/analysis/`

重点不是多写文档。一旦输出被分类并持久化，它就进入了仓库记忆。聊天窗口是临时上下文。文件是仓库记忆。

## 代码是当前实施事实，不是唯一事实

代码是当前实施的事实源。类型和测试保护当前行为。带优先级的架构所有者文档定义吸引子：系统长期应向哪里收敛的结构。日志、Bug、分析、测试记录轨迹和外化记忆。

这些不冲突。冲突发生在两种情况下：

- 文档开始复述脆弱的实现细节
- 文档完成被当作代码已经正确的证明

OpenSpec 的行为优先边界也在尽力避免第一个问题：行为规格应描述可验证的行为，而非内部实现细节。Flux 进一步强调第二个问题：即便文档陈述了正确行为，它也不能替代当前仓库验证。真正的闭环必须回到代码、测试、所有者文档、日志和审计证据。

## 真正的差异

OpenSpec 解决这个问题：如何通过结构化的 specs、changes、deltas 和 archives 组织行为规格更新。其焦点是规格的演化流程。

AGE 解决这个问题：当 AI 高速扩展状态空间时，系统如何先定义吸引子，再用计划、验证、审计、日志、Bug、分析、测试等夹具来保持轨迹收敛？

两种工具解决的问题不在同一层。OpenSpec 在结构化规格工作流上强。Flux/AGE 在通过带优先级的架构所有者文档定义吸引子，再用自由但职责有界的文档路由和严格闭环夹具来让仓库随时间收敛上更强。

从规格驱动开发到吸引子引导工程的转变，不是从"写规格"回到"不写规格"，而是从"把变更组织成规格更新"走向"定义系统长期应向哪里收敛，并让每轮 AI 生成都被拉回那个结构"。

## 普通项目可以直接用的

不需要复制 Flux 的全部治理。

**第一，文件入/文件出。** 先把输入放进文件，再 `@` 给 AI。把输出写入 `docs/`，而不是只留在聊天窗口。这只需几分钟，但能让 AI 依赖可追溯的仓库记忆，而不是上下文记忆。

**第二，为核心业务写一份架构文档，定义业务吸引子。** 不要写代码导览，写事实源、状态转移、所有权边界和常见误解。

**第三，为复杂变更加写轻量计划。** 包含当前基线、目标、不做什么、执行条目、证明条目和闭环条件。完成前用独立会话或独立审查者复核。

**第四，把重复出现的问题变成仓库记忆。** 手动问题进测试，复杂 Bug 进 Bug，研究结论进分析，高频错误进审计脚本。

规格更新是必要层，系统收敛仍需要吸引子。
