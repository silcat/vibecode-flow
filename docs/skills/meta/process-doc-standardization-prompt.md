# 流程目录标准化提示词

对 `docs/process/` 下的流程文件和阶段文件按以下规则审计并重构。

## 核心原则

1. **归权责**：每个决策只在一个文件定义，其余文件只引用不重复。
2. **阶段不感知调用方**：阶段 README 不内置执行条件、不列调用它的流程名、不在首先阅读中引用上下游阶段。
3. **flow 持有跳过逻辑**：哪个阶段可跳过、什么条件跳过——由 flow 文件（main.md / bug.md）的序列表持有。
4. **中英分界**：面向人的流程概念用中文（轻量/完整/项目），面向机器的字段值用英文（standalone/master/sub）。
5. **首先阅读按场景路由**：列出"如果你需要 X，先读 Y"的表，不列文件清单。
6. **首先阅读仅引核心工具**：阶段 README 的首先阅读表只列本阶段核心执行工具（如 audit-prompt.md），不列上下游阶段的 README——阶段不感知谁调用它。

## 判定树

```
打开一个文件
├─ 是 flow 文件（main.md / bug.md / program-management.md）？
│   ├─ 序列表每行加了条件列？没有 → 加
│   ├─ 文件角色段存在？没有 → 加
│   ├─ 首先阅读段存在？没有 → 加（引用 ≥ 1 即可）
│   ├─ 属于/不属于段存在？没有 → 加
│   └─ 更新原则段存在？没有 → 加
│
└─ 是阶段 README（stages/*/README.md）？
    ├─ 文件角色段存在？没有 → 加一句话本职（不列流程名）
    ├─ 执行条件段存在？是 → 删除（移到对应 flow 文件）
    ├─ 首先阅读段存在？
    │   └─ 引用 ≥ 1（含本阶段核心执行工具）？没有 → 加场景路由表
    │   └─ 引用了上下游阶段？是 → 删除那些行，只留核心工具
    ├─ 属于/不属于段存在？是 → 删除（叶子阶段不需要）
    ├─ 更新原则段存在？是 → 删除（叶子阶段不需要）
    ├─ "失败回退"更名为"回退"？没统一 → 统一
    ├─ 退出段是否写死了单一路径？是 → 保持（目前所有阶段退出路径在全部入口下一致）
    └─ 产出段存在？审计/计划/实施类阶段应加 → 加（日期前缀命名）
```

## 删除 flow 文件

当某个 flow 文件被删除，但其阶段仍被其他 flow 使用（如 audit.md 被删除，但 audit/plan-audit/closure 阶段仍被 main.md 使用）：
- 删除 flow 文件本身
- 更新 `routing.md`：移除路由表对应行和流程文件段对应条目
- 阶段目录不动

## 通用格式

### flow 文件

```markdown
# <标题>

## 文件角色
<一句话>。路由触发条件：<条件>。

## 首先阅读
| 如果你需要… | 先读 |
|-------------|------|
| ... | ... |

## <序列定义>
| 阶段 | 条件 | 模块 |
|------|------|------|

## 属于这里的
## 不属于这里的
## 更新原则
```

### 阶段 README

```markdown
# <阶段名>

## 文件角色
<一句话本职>。

## 首先阅读（引用 ≥ 1 时加）
| 如果你需要… | 先读 |
|-------------|------|
| ... | ... |

## 执行
## 红线（有硬约束时加）
## 产出（审计/计划/实施类阶段加，日期前缀命名）
## 退出
## 回退（可能失败时加）
```

## 产出命名约定

审计、计划、实施等产出类阶段，产出文件按以下模式命名：

```
docs/<目录>/YYYY-MM-DD-<topic>.md
```

- 日期在前，天然区分先后（同一工作项可能多次审计）
- topic 固定，区分不同类型（如 `requirement-baseline-audit`、`plan-audit`、`closure-audit`）

## 执行条件归属规则

- 阶段 README **不设**执行条件
- flow 文件序列表中每行标注条件列
- 条件写清是"始终"还是具体触发条件
- scope 判级本身即条件——判为轻量则跳过 audit/plan/plan-audit/closure，不重复在阶段 README 中表

## 修改流程

1. 按字母序逐个处理阶段文件，每次生成提议版 → 确认 → 应用
2. 阶段文件处理完后，处理 flow 文件
3. 每次改动后验证交叉引用无断裂
