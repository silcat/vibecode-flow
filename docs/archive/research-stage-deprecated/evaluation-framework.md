# 技术评估框架

对技术选型进行结构化评估，基于 6 维度框架输出推荐结论和方案对比。

本文件是阶段 ④ 技术调研的核心方法论。入口、退出条件和后置步骤见同目录下的 `README.md`。

## 评估原则

**胶水开发优先**：强依赖复用现有成熟库。评估时优先考虑已有完整实现的方案，而非自研成本。本项目只写编排/调度/适配代码，不造轮子。

## 6 维度评估框架

### 一、功能匹配

| 维度 | 评估内容 |
|------|---------|
| 需求覆盖率 | 满足需求的比例？哪些需求需要自研补充？ |
| 功能缺口 | 缺的功能是核心路径还是边缘场景？缺口能否通过插件/扩展补上？ |
| 过度设计风险 | 引入了不需要的功能复杂度？实际只用 20%，剩下 80% 是负担 |

### 二、技术质量

| 维度 | 评估内容 |
|------|---------|
| 成熟度 | 生产环境验证案例？大厂背书？已知踩坑记录？ |
| 性能基准 | 与需求场景匹配的性能数据（QPS、延迟、内存），不是"感觉快" |
| 安全记录 | CVE 历史、依赖链审计、最近漏洞修复时效 |
| 错误处理 | API 的错误模型清晰？失败模式可观测？ |

### 三、集成成本

| 维度 | 评估内容 |
|------|---------|
| 技术栈兼容 | 语言/框架版本/构建工具链与当前基线是否冲突？ |
| 胶水代码量 | 接入需要多少适配层？开箱即用还是需要大量包装？ |
| 依赖传染 | 引入的传递依赖数量？是否与已有依赖冲突？ |
| 配置复杂度 | 启动到可用需要多少配置项？默认值合理？ |

### 四、可维护性

| 维度 | 评估内容 |
|------|---------|
| API 设计质量 | 接口一致、可预测？命名约定？破坏性变更频率？ |
| 升级路径 | 主版本升级成本？迁移指南？ |
| 测试友好 | 提供测试工具/fixture/mock？自身测试覆盖率？ |
| 可替换性 | 将来换掉它的解耦成本？ |

### 五、社区与生态

| 维度 | 评估内容 |
|------|---------|
| 维护活跃度 | 最近 release 时间；issue/PR 响应时效（不看 commit 频率） |
| Star 趋势 | 近 6 个月增速和趋势（不看绝对值） |
| 文档质量 | 可运行 quickstart？API 文档完整？常见问题覆盖？ |
| 生态插件 | 成熟的中间件/插件？形成事实标准？ |

### 六、团队与组织

| 维度 | 评估内容 |
|------|---------|
| 学习曲线 | 团队平均上手时间？概念模型与团队已有经验接近？ |
| 许可证 | 兼容商业使用？传染性条款（如 AGPL）？ |
| 供应商风险 | 单点依赖？商业公司维护还是社区驱动？停维历史？ |
