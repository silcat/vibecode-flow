# Bug 修复笔记编写指南

## 用途

使用 `docs/bugs/` 存放非显而易见的回归、微妙根因和应影响未来审查的修复。

目标不是重复完整的 diff。目标是保留出了什么问题、如何发现的、为什么发生、以及如何防止其复发。

## 何时编写 Bug 笔记

当至少满足以下之一时编写：

- Bug 具有非显而易见的根因
- Bug 跨越模块或包边界
- Bug 看起来像一件事但实际由另一层导致
- 修复添加或变更了回归测试
- 未来的重构可能轻易重新引入相同问题

不要为每个微小拼写错误或微不足道的一行修复编写。

## 必需章节

每个 Bug 笔记应包含以下章节。保持每章简短。

### 1. 问题

用 2—5 行描述观察到的症状。包括什么出错了、在哪里、最小可复现行为，以及影响或严重程度（受影响用户、数据完整性、爆炸半径）。

### 2. 复现

描述所需的环境状态和触发动作，以便未来读者可以复现。包括确切步骤、任何前置条件（如"必须以管理员身份登录""需要 2000 并发请求"），以及最小复现脚本（如适用）。

### 3. 诊断方法

此章为必填。描述问题是如何定位的，而非仅最终根因。

包括：

- 什么使诊断困难
- 首先检查了什么及为什么
- 测试和拒绝了哪些假设（如果诊断非平凡则必填）
- 什么直接证据确认了真正原因

如果诊断简单明了（单一确凿指标或日志），明确说明并解释为何不需要迭代——例如"崩溃堆栈精确指向我们代码中的 return 语句（第 2 帧是我们的代码）"。否则，至少包含一条被排除的替代路径。

### 4. 根因

用 1—3 个要点解释真正原因。提及涉及的实际模块或子系统。如果 Bug 有多个原因，清晰地分开它们。

**边界规则：** 诊断方法涵盖调查过程和证据链。根因涵盖 Bug 为何在系统内部机制层面发生的解释。两章不应重复相同信息。对于调查直接揭示机制（因果链本身就是证据链）的 Bug，两章可合并为 `*诊断与根因` 并附说明解释原因。

### 5. 修复

从设计意图角度解释解决方案，而非逐行代码变更。包括改了什么、在哪里、以及为何解决了根因。

### 6. 测试

列出添加或更新的回归覆盖。包括测试文件路径、测试保护什么，以及测试级别（单元/组件/集成/E2E）。对于仅 E2E 覆盖，解释为何较低级别不可行。

如果自动化测试不切实际（竞态条件、时序、第三方依赖），记录手动验证步骤并明确说明为何未添加自动化测试。

### 7. 受影响的产物

列出变更的代码文件、配置文件、部署清单或基础设施定义。使用 `路径/到/文件.ts:行号` 格式并附简短注释。不要粘贴大段 diff。

### 8. 为未来重构者注意

添加 1—3 个要点，描述未来变更应小心不要破坏的内容。指定受影响产物中的具体代码模式和具体的错误场景（如"如果某人换成另一个连接池库，新驱动可能依赖 `finalize()` 而非显式 `close()`"）。此节很重要，因为这些笔记的主要价值是长期记忆。

### 9. 预防缺口（可选）

添加 1—2 个要点，说明缺失了什么审查、测试或流程步骤导致此 Bug 被发布。这是关于系统性缺口，而非个人追责。示例："没有负载测试演练 2000 并发请求路径"或"此页面不存在基于路由的导航测试。"

## 推荐模板

```md
# 0X 简短 Bug 修复标题

## 问题

- 什么出错了
- 在哪里出错
- 最小可见症状
- 影响或严重程度

## 复现

- 环境和前置条件
- 触发步骤
- 最小复现脚本（如适用）

## 诊断方法

- 诊断难度（为什么难，或"简单明了"）
- 调查路径（首先检查了什么）
- 被拒绝的假设（如果诊断非平凡）
- 确认问题的决定性证据

## 根因

- 实际原因 1
- 实际原因 2
- （如果证据链本身就是机制，可与诊断方法合并为 `*诊断与根因`）

## 修复

- 主要变更 1
- 主要变更 2

## 测试

- `路径/到/测试文件` — 验证什么（级别：单元/组件/集成/E2E）
- 如无自动化测试：手动验证步骤及原因

## 受影响的产物

- `路径/到/文件:行` — 注释

## 为未来重构者注意

- 风险或不变量 1（具体模式 + 具体错误场景）
- 风险或不变量 2

## 预防缺口（可选）

- 缺失了什么审查/测试/流程步骤
```

## 文件名指引

对于中小项目，以下两种风格均可接受：

- 编号式：`docs/bugs/01-简短-bug-名称.md`
- 日期式：`docs/bugs/YYYY-MM-DD-简短-bug-名称.md`

如果期望 Bug 笔记成为长期参考库，优先选择编号文件名。

## 验证清单

提交 Bug 笔记前，验证：

- [ ] 问题包含影响或严重程度
- [ ] 复现包含环境、触发条件和最小步骤
- [ ] 诊断方法描述了调查过程，而非仅原因
- [ ] 诊断方法包含被拒绝的假设（或明确说明"简单明了"并附原因）
- [ ] 根因指出具体模块或子系统；或合并章节已标注
- [ ] 修复解释了为何变更有效，而非仅做了什么变更
- [ ] 测试包含测试级别（单元/组件/集成/E2E），或记录了手动验证并附明确原因
- [ ] 为未来重构者注意列出具体模式和具体错误场景

## 其他规则

- 每个非平凡 Bug 修复应添加或更新自动化测试覆盖。
- 如果创建了 Bug 笔记，包含测试证明路径或验证证据。
- 使用 `docs/baseline/architecture/` 存放当前设计真相，`docs/bugs/` 用于记住重要失败和修复为何存在。
