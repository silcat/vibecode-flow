# API 版本化规范

> 触发场景：新增 API 版本、废弃旧版本、判断版本间兼容性

## 版本策略

### 推荐方案：URL 前缀版本

```
/api/v1/users
/api/v2/users
```

- 版本号仅用主版本（`v1`、`v2`），不用次版本（非 `v1.1`）
- 不同主版本之间不保证兼容
- 同一主版本内的新增字段必须向后兼容

### 备选方案（如需要）

Header 版本：`Accept: application/vnd.myapi.v2+json`

仅在 URL 前缀不可行时使用（如需要细粒度内容协商），默认选用 URL 前缀方案。

## 向后兼容规则

### 允许（不升级主版本）

- 新增可选字段（有默认值）
- 新增新的 API 端点
- 修复 Bug（行为与文档一致但实现有偏差）
- 放宽参数校验（之前过于严格）

### 禁止（必须升级主版本）

- 删除或重命名已有字段
- 修改已有字段的类型
- 修改已有端点的 URL 路径
- 收紧参数校验（之前允许的值现在拒绝）
- 修改认证/鉴权方式
- 修改分页默认值

## 废弃流程

```
v1 稳定期 ──→ v2 发布 → v1 标记废弃 → v1 移除
              ←── 至少 1 个发布周期 ──→
```

1. **v2 开发**：新功能在新版本开发，v1 继续正常服务
2. **v2 发布**：v2 上线，v1 仍在运行
3. **标记废弃**：v1 端点添加 `@Deprecated` 注解 + 响应头 `Sunset: Sat, 01 Aug 2026 00:00:00 GMT`
4. **通知消费方**：通过变更日志 / API 文档 / 邮件通知所有已知消费方迁移
5. **监控迁移**：观察 v1 调用量下降至接近零
6. **移除 v1**：在下一个主版本发布时移除 v1 代码

### 实现要点

- 废弃版本：Controller 加 `@Deprecated` 注解，响应头注入 `Sunset` 和 `Deprecation` header
- 活跃版本：与废弃版本并存，各自独立 Controller
- Gateway 层：每个主版本独立路由，不做版本转换

## 禁止事项

| 禁止 | 原因 |
|------|------|
| 不通知消费方直接删除旧版本 | 破坏下游系统 |
| 在 v1 接口上直接修改行为 | 等同于不兼容变更 |
| 仅升级版本号而无实际变更 | 混淆版本语义 |
| 版本号超过 2 个活跃版本 | 增加维护负担，v1 应尽快移除 |
