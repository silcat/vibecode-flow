# 真源与优先级

## 用途

此文件定义哪个工件回答哪个问题。

用它来避免混淆稳定真源、执行笔记和历史上下文。

## 按问题排序的优先级

### 现在应该构建什么？

主源：

- `docs/work/`（活跃需求与计划）

辅助源：

- `docs/work/<branch>/discussion.md`（需求澄清讨论）

规则：

- 聊天中的原始需求需落地为 `docs/work/` 下的文件后才成为真源
- 若活跃需求与讨论记录存在分歧，先更新需求文件，不要靠聊天记忆静默推进

### 当前支持的系统行为是什么？

主源：

- `docs/baseline/architecture/`（架构层所有者文档）
- `docs/baseline/standards/`（项目级规范）

规则：

- 架构文档定义模块边界、数据流、技术结构
- 规范文档定义编码契约和实现约束
- 需求文件可驱动变更，但稳定行为应收敛到架构和规范文档中

### 当前支持的技术结构是什么？

主源：

- `docs/baseline/architecture/`

规则：

- `docs/baseline/architecture/` 拥有技术边界、模块职责和跨切面实现规则

### 数据库真源是什么？

主源：

- `src/` 下的数据库模型定义（entity 类、mapper XML、DDL 迁移脚本）

规则：

- 数据库定义由模型/schema 工件拥有，不由计划文本或散文文档拥有
- 文档可解释意图，但模型文件是真源

### API 契约真源是什么？

主源：

- `src/` 下的 Controller 定义、Feign 接口定义、请求/响应 DTO

规则：

- 散文文档可总结 API 意图，但可执行或结构化的 API 契约优先

### 外部集成真源是什么？

主源：

- 外部系统的集成契约文档
- 已提交的适配器配置或集成测试

规则：

- 不要仅凭 UI 需求为外部系统编造行为


### 关键业务流程的真源是什么？

主源：

- `docs/baseline/architecture/business-flows.md`（索引）
- `{service}/docs/flows/`（各模块下的具体流程文件）

规则：

- 跨模块的端到端流程序列、通道和失败策略由此文件体系拥有
- 流程中引用的具体参数/字段以活代码为准，但调用序列和失败处理以此文件为准
- 完全在单模块内部完成的流程不在此记录
### 环境/部署真源是什么？

主源：

- `docker-compose.yml`
- 各服务的 `application.yml` / `application-*.yml`
- Nacos 配置中心的已提交配置

规则：

- 计划和文档可描述部署意图，但已提交的部署/配置工件是操作性真源

### 切片应如何执行和关闭？

主源：

- `docs/work/` 下的计划文件

规则：

- 计划是执行契约，不是长期所有者文档

### 执行过程中实际发生了什么？

主源：

- `docs/logs/`

辅助源：

- `docs/bugs/`
- `docs/retro/`

### 未来 AI 会话应从重复失败中学到什么？

主源：

- `docs/skills/`（可复用提示词和操作手册）
- `docs/retro/`（可复用工程教训和警示模式）

## 冲突裁决

- 若原始输入与整理后的需求不一致，先更新 `docs/work/` 或重新发起澄清，再写代码。
- 若需求与所有者文档不一致，先判断需求是否改变支持的基线；然后明确更新 `docs/baseline/architecture/` 或 `docs/baseline/standards/`。
- 若活代码与所有者文档不一致，视为实施漂移或文档过时；不要静默选择一方。
- 若解决冲突会改变用户可见行为、数据/模型结构、API 行为、认证/权限行为或外部集成行为，停止并请求确认。
- 若验证失败，即使实施看似完成，计划也不关闭。
- 若模型/schema 文件与散文文档在数据库真源上不一致，模型/schema 文件优先；有意更新散文文档或模型。

## 遗留或文档过时模式

当 `docs/baseline/context/project-context.md` 将文档新鲜度标记为 `stale`、`unknown` 或 `partially stale` 时使用此模式。

- 活代码和可执行契约是当前行为的证据，不自动是期望行为。
- 所有者文档仅在对照活代码、需求和人类/产品意图重新验证后才是目标吸引子。
- 在改变行为前，于需求、讨论、分析或计划文件中将每个冲突分类为 `实施漂移`、`文档漂移` 或 `有意的遗留行为`。
- AI 自治默认降为 `research-only` 或 `plan-first`，直到基线审计或人类确认记录哪些应保留、哪些应变更。对于 `partially stale`，此限制仅适用于需求、所有者文档、代码地图路由或触及代码区域尚未验证为新鲜的切片。
- 不要在未记录漂移分类的情况下"修复"代码以匹配过时文档，或重写文档以匹配代码。

## 简单经验法则

- 稳定行为和结构属于所有者文档
- 执行属于计划和日志
- 历史和诊断属于 bugs、retro 和 lessons
