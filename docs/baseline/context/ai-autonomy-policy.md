# AI 自治策略

## 用途

此文件定义 AI 代理何时可以直接执行、何时必须停止等待人类输入。

保持简短且与项目紧密相关。当团队希望 AI 采取更多或更少主动时更新此文件。

AI 可以通过将工作标记为更受限来收紧此文件，但 AI 不得放松保护区、将 `ask-first`/`blocked`/`research-only` 类工作改为 `implement`、或在没有明确人类确认或标有人类批准的所有者文档证据的情况下移除阻塞条件。

AI 编写或 AI 修改的文档（包括所有者文档）不得作为放松自治、清除阻塞条件、将文档标记为新鲜、或降级保护区的证据，除非人类明确批准该证据。

## 自治级别

在 `docs/work/registry.md` 和活跃计划中使用以下标签：

- `implement` — AI 可在阅读所列需求、所有者文档和验证命令后直接实施。
- `plan-first` — AI 可起草或更新计划，但实施需等待计划审计及下表中保护区所需的批准。
- `ask-first` — AI 在修改代码或用户可见行为前必须先询问。
- `research-only` — AI 可检查、总结并提出方案，但不得修改产品行为。
- `blocked` — AI 在阻塞条件被文件解决或人类确认前不得继续。

## 审查者可用性

为本项目设置一个值：

- 审查者可用性：`human`

规则：

- `human` — 对所需的计划和闭环审计使用该审查者。
- `none` — 冷重放仅可用于非保护区、非高风险计划。冷重放不是第二个审查者，而是在搁置实施上下文后执行的书面自检。
- 保护区、未解决的产品风险、或真源冲突仍需人类审查，否则必须保持阻塞。

## 文档新鲜度


### 值域

- `fresh` — 文档与活代码一致，可信任。
- `stale` — 文档与代码存在已知漂移。
- `unknown` — 尚未执行基线审计，可靠性未评估。
- `partially stale` — 部分切片已验证新鲜，其余区域未验证。

### 维护规则

- **AI 可降级**：检测到代码与文档漂移时，AI 可降为 `stale`、`unknown` 或 `partially stale`，须注明原因和范围。
- **仅人类可升回 `fresh`**：AI 编写的文档不得作为升回证据。
- `unknown` 与 `stale` 自治效果相同：AI 在触及未验证区域时降为 `research-only` 或 `plan-first`。

## AI 可直接执行的条件

本节条件适用于进入主流程的非琐碎工作（功能/设计/架构/非琐碎实施）。以下路径按路由协议独立执行，不受本节门控约束：
- 琐碎修复（单文件 + <15 行 + 无契约变更）→ 实施→验证→日志
- 表层 Bug（拼写/空指针/样式）→ 诊断→修复→验证→日志
- 纯信息问题 → 直接回答→退出
- 审计/验证工作 → 运行审计提示词→记录发现→修订文档

满足以下全部条件时 AI 可直接执行：

- 工作项标记为 `implement`，或用户直接请求的本地低风险变更
- 活跃需求有具体的验收标准
- 活跃所有者文档已在 `docs/baseline/context/project-context.md` 中列出
- 对于 registry.md 中的工作，状态为就绪、无失效链接、无需缺失的计划
- `docs/baseline/context/project-context.md` 中的验证命令是真实命令，非占位符
- 本文档中的保护区占位符已替换为真实条目或明确的 `none`
- 文档新鲜度为 `fresh`，或活跃切片已明确验证需求、所有者文档、codebase-map 路由及触及代码区域均为新鲜
- 任务不触及下方保护区
- 未决问题明确标记为非阻塞

## AI 必须询问或停止的条件

- 当需求或所有者文档模糊时变更产品范围
- 在没有所有者文档和测试策略的情况下变更数据库/模型结构、数据删除、支付、认证、权限、部署或外部集成行为
- 为未在已提交的集成文档或测试中描述的外部系统编造行为
- 因验证命令缺失、损坏或过慢而跳过必需的验证
- 在审计、验证、文档或检查清单证据缺失的情况下关闭计划
- 当活代码与所有者文档冲突且解决冲突会改变用户可见行为或公共契约时继续推进
- 在没有人类确认或人类批准的所有者文档证据的情况下放松自治标签、保护区规则或阻塞条件
- 当文档新鲜度为 `stale`、`unknown` 或 `partially stale` 时继续实施；先执行基线调研或 plan-first 对齐切片

## 保护区

以下保护区内的变更必须遵守对应规则：

| 区域 | 规则 | 所需证据 |
|------|------|---------|
| 支付/退款/资金流转 | ask-first | 所有者文档 + 测试 |
| Gateway 认证/鉴权过滤器 | ask-first | 所有者文档 + 全量集成测试 |
| 数据库 schema（DDL） | ask-first | 所有者文档 + 迁移脚本 |
| Kafka topic 定义或消费者组 | ask-first | 所有者文档 + 集成测试 |
| 跨服务公共契约（≥2 个微服务） | ask-first | 所有者文档 + 契约测试 |
| API 版本废弃或版本化策略 | ask-first | 所有者文档 + 兼容性分析 |

保护区规则含义：

- `ask-first` — 人类批准后才可规划或实施。
- `plan-first` — AI 可起草计划，但实施需等待计划审计加上表中列出的所需证据。若审查者可用性为 `none`，实施保持阻塞。

## 工作选择规则

若用户要求 AI 继续工作但未指定任务，选择 `docs/work/registry.md` 中优先级最高、自治级别为 `implement` 且无阻塞条件的工作项。

实施所选工作项前，重新检查计划触发条件。`Plan: none` 不免除计划指南。

用户对本地低风险编辑的直接请求不需要 plan-registry 条目，但仍需满足无计划路径和验证规则。

若无安全的 `implement` 工作项，汇总排在最前的阻塞、`plan-first` 或 `ask-first` 项，并请求用户决策。
